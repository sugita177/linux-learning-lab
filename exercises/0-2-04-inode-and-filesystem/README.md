# 0-2-04. ファイルシステムの裏側（inodeとリンク・削除済みファイルの正体）

この節では、Linuxファイルシステムの核心である **inode（アイノード）** の構造、ハードリンクとシンボリックリンクの決定的な違い、および本番障害の定番である **「ファイルを消したのにディスク容量が空かない現象」** とそこからのデータ復元技術をハンズオンで解明しました。

---

## 1. inode とファイルの実体（参照カウントモデル）

私たちが普段目にする「ファイル名」は、ファイルの実体そのものではなく、ディレクトリエントリに記録された **「名札（ラベル）」** に過ぎません。

ファイルの実体（サイズ、パーミッション、作成日時、データブロックへのポインタ）は、カーネルによって **`inode`（index node）** というデータ構造で一意の番号（inode番号）とともに管理されています。

> **プログラミング言語のメモリ管理との一致**：
> - **inode（実体データ）** ＝ メモリ上のオブジェクト
> - **ファイル名（ハードリンク）** ＝ オブジェクトを指す変数（ポインタ）
> - **リンク数（Links）** ＝ 参照カウント（Reference Count）
> - **`rm` コマンド** ＝ `unset($var)`（参照を1つ減らす `unlink` システムコール）
> - **領域解放の条件** ＝ 参照カウント（リンク数およびプロセスからのFD参照数）が完全に0になったとき

## 2. ハードリンク vs シンボリックリンク (`01_inode_and_links.sh`)

| 項目 | ハードリンク (`ln`) | シンボリックリンク (`ln -s`) |
| :--- | :--- | :--- |
| **実体 (inode)** | **元ファイルと全く同じ inode番号 を共有** | **新しい独立した inode が作成される** |
| **リンク数** | リンク数が +1 される | リンク数は変わらない（1のまま） |
| **属性表示** | 通常ファイル (`-rw-r--r--`) | リンクファイル (`lrwxrwxrwx`) |
| **元ファイルを `rm` した場合** | **平然と読める**（リンク数が -1 されるだけで実体は残る） | **リンク切れ**（`No such file or directory`） |

### 実験結果
```text
=== 1. リンク作成後の比較（inode番号とリンク数） ===
295064 -rw-rw-rw- 2 root root 12 Nov  5 15:14 hardlink.txt  # inode 295064 (リンク数 2)
295064 -rw-rw-rw- 2 root root 12 Nov  5 15:14 original.txt  # inode 295064 (リンク数 2)
295065 lrwxrwxrwx 1 root root 12 Nov  5 15:14 symlink.txt -> original.txt # 別inode

=== 2. original.txt を rm (unlink) した後 ===
295064 -rw-rw-rw- 1 root root 12 Nov  5 15:14 hardlink.txt  # リンク数が 1 に減っただけ
hardlink の中身: hello linux (そのまま読める！)
symlink の中身: cat: symlink.txt: No such file or directory (リンク切れ)
```

## 3. 削除済みファイル掴みっぱなしとデータ救出 (`02_deleted_file_held_by_process.sh`)

### 「ファイルを消したのにディスク容量が空かない」理由
カーネルがディスクから実体データブロックを解放する真の条件は：
1. **リンク数（ファイル名）が 0 であること**
2. **かつ、「どのプロセスもそのファイルを開いていない（FD参照数が0）」こと**

Webサーバー（Nginx / PHP-FPM）や監視ツール（`tail -f`）がログファイルを開きっぱなしにしている場合、`rm` でファイル名を消しても、カーネルは **「まだプロセスが使用中である」と判断し、ディスク容量を解放しません**。

### `(deleted)` の出現とデータ救出
プロセスが開いている最中にファイルを `rm` すると、`/proc/<PID>/fd/` に以下のような表示が現れます：

```text
lr-x------ 1 root root 64 Nov  6 02:43 3 -> '/tmp/important.log (deleted)'
```

- **奇跡のデータ復元**:
  ファイル名が消えても、プロセスが繋がっている **FD口（`/proc/<PID>/fd/<番号>`）** から直接データを吸い出すことで、失われたはずの重要データを100%復元できます。
  ```bash
  cat /proc/$APP_PID/fd/3 > /tmp/restored.log
  ```

### ★実務の調査コマンド：犯人プロセスの特定 (`lsof +L1`)
「削除したのにディスクが100%のまま空かない」本番障害では、以下のコマンドで削除済みファイルを掴んでいる犯人プロセスを特定します：
```bash
lsof +L1
```
（※ `+L1` は「Links が 1 未満（＝0）の開かれているファイル」を抽出するオプション）
該当プロセス（Nginx等）をリロード/再起動することで、初めてFDが閉じられてディスク容量が解放されます。
